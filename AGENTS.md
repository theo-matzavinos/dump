# Article audience and explanations

- Write articles so entry-level and junior engineers can follow them. Do not assume Angular experience or seniority implies knowledge of JavaScript, browser behavior, or underlying web fundamentals.
- Explain the concrete mechanism step by step before introducing terminology or framework APIs. Make prerequisites explicit, define unfamiliar terms without relying on other unexplained terms, and simplify the explanation without sacrificing technical accuracy.
- State prerequisites as a plain line ("you'll need X for Y"), not only as links. Define each term once, at first use; link to the article that teaches it instead of re-teaching it.
- Link only to articles that already exist. Don't mention articles that aren't written yet ("a later article covers this"); state what's out of scope without promising where it's covered. This applies to outlines too.
- Show the smallest working version before edge cases, validation, or hardening.

# Article voice

- Write in a neutral casual voice: use contractions, address the reader as "you", and connect ideas with "so", "but", "that's why". No first person and no anecdotes.
- Say what something is and does before what it isn't. Use a negation only to correct a misconception readers plausibly hold, and name that misconception first.
- Name the concrete actor (the page component, the browser's cache, the root injector) instead of abstract nouns such as owner, consumer, contract, boundary, or responsibility.
- Use plain topic headings that say what the section covers, not "X, not Y" slogans.
- Vary openings; don't reuse the three-mysteries-plus-bolded-thesis template. Close by answering whatever question or problem the opening raised.
- Write words out instead of slash compounds such as "correct/drop".
- Keep authoring and verification notes out of article prose. Give one setup and versions note per article, and state scope limits once.

# Article structure

- Use the task board as the running example where the topic allows, and keep code style consistent across the series.
- Show code in small slices, each followed by what to notice. Link or collapse full files instead of dumping long listings, and keep styling classes out of examples that aren't about styling.
- Keep the Contents list. Limit closing quizzes to three or four questions that test the article's main point.
